# ADR 0003 — Local database, Prisma, and test-database safety

- **Status:** Accepted
- **Date:** 2026-10-05
- **Phase:** 2 (Database)
- **Decisions:** P1–P7 (approved 2026-10-05)

## Context

The MVP needs a relational database with strong integrity guarantees, a reproducible local setup on
an 8 GB M1 machine, separate development and test databases, and no risk of tests destroying
development data. Prisma 7 changed several defaults (driver adapters required, config file, no
automatic `.env` loading, no automatic client generation after `migrate dev`).

## Decision

### PostgreSQL in Docker Compose

- Image `postgres:16.15-alpine3.24`, pinned to the multi-arch index digest
  `sha256:721873c34ceb9f8d8fc265984940dc982404c105f19ad51be9fdc5970a6080ea`. Verified before
  pinning: the index includes `linux/arm64/v8` (local container reports `arm64`, PostgreSQL 16.15
  on aarch64).
- Port published on `127.0.0.1` only (`POSTGRES_PORT`, default 5432) (P7).
- `mem_limit: 512m`; server memory settings sized to fit (`shared_buffers=128MB`,
  `effective_cache_size=256MB`, `work_mem=4MB`, `maintenance_work_mem=64MB`, `max_connections=30`).
- Health check: `pg_isready` every 5 s; `pnpm db:up` waits for healthy (`--wait`).
- Named volume `pgdata`. Never `docker compose down -v`; stop with `pnpm db:stop`.
- `docker/postgres/init/01-create-test-database.sql` creates `sprikle_ops_test` when the volume is
  first initialized.

### Credentials (P4)

`.env.example` contains no usable password. `pnpm env:init` (`scripts/create-local-env.ts`) creates
`.env` only if it does not exist (exclusive create, mode `0600`), generates a random 24-byte
base64url password, and writes it into `POSTGRES_PASSWORD`, `DATABASE_URL`, and
`TEST_DATABASE_URL`. The password is never printed. Compose refuses to start without credentials.

### Prisma 7.10

- `prisma`, `@prisma/client`, `@prisma/adapter-pg` pinned to **7.10.0** (`prisma`'s `latest` tag
  is `8.0.0-rc.20`, a release candidate). `pg` 8.23.1 and `@types/pg` 8.23.1 were verified
  independently (`@prisma/adapter-pg` requires `pg ^8.16.3`).
- Generator `prisma-client`, ESM output to `src/generated/prisma` (gitignored). The client is
  generated by `postinstall`, `pnpm build`, and `pnpm typecheck`; Prisma 7's `migrate dev` does
  **not** run generate.
- `prisma.config.ts` loads `.env` with Node's `process.loadEnvFile()` (verified: it never overrides
  variables already set), so no `dotenv` dependency. `datasource.url` is optional, so `generate`,
  builds, and unit tests work without a database.
- No `shadowDatabaseUrl`: `migrate dev` creates and drops a temporary shadow database on the local
  server (verified: none left behind) and never uses the development or test databases.
- pnpm build scripts: only `@prisma/engines` is allowed; its postinstall downloads Prisma's native
  schema engine (`schema-engine-darwin-arm64`, ~25.6 MB) from Prisma's official binary host. `prisma`'s
  preinstall (a Node version check) stays blocked.
- snake_case database names via `@map`/`@@map` (P1).
- CHECK constraints and append-only triggers in migration SQL (P3); see
  [data-model.md](../data-model.md) for the list, their limits, and how Prisma treats custom SQL.

### Runtime client and timeouts

`src/server/db.ts` creates one lazily initialized client (cached on `globalThis` for dev hot reload)
with a `pg` pool: `max: 5`, `connectionTimeoutMillis: 1500`, `statement_timeout: 10000`
(server-side), `query_timeout: 10000` (client-side), `application_name: sprikle-ops`.

The health check (`src/server/health.ts`) runs `SELECT 1` inside a transaction with
`SET LOCAL statement_timeout = 1000`, races it against a 2 s budget, and returns `ok` or
`unavailable`. Database work abandoned by the race is still bounded by the driver and server
timeouts. Late failures are absorbed (no unhandled rejections). Logs contain only an error class
and a short code (for example `P1001`, `HEALTH_TIMEOUT`); responses never contain error text,
URLs, hosts, or credentials.

### Test-database safety (fail closed)

- `tests/helpers/database-safety.ts` validates the **original** `DATABASE_URL` and
  `TEST_DATABASE_URL` before any test process overrides `DATABASE_URL`, and refuses unless:
  `NODE_ENV=test`; both URLs parse as `postgresql://`; the test database is exactly
  `sprikle_ops_test`; the test host is `localhost`, `127.0.0.1`, or `[::1]`; no connection-redirecting
  query parameters (`host`, `dbname`, `options`, …); development and test target different
  databases. Refusal messages never include URLs.
- `pnpm db:test:prepare` runs the guard, then `prisma migrate deploy` (non-destructive). It never
  resets, drops, or truncates.
- Test cleanup truncates an explicit table list (never `_prisma_migrations`), without `CASCADE`,
  inside a transaction that first checks `current_database() = 'sprikle_ops_test'` on the same
  connection.
- Integration files run serially.
- **CI (later):** the localhost restriction is intentional for Phase 2. CI will need an explicit,
  trusted database-host configuration (for example an allow-listed service-container host) rather
  than loosening this rule.

### Test commands (P5)

`pnpm test` and `pnpm check` need no database. `pnpm test:integration` (runs `db:test:prepare`
first) and `pnpm check:full` require the local test database.

## Consequences

- The initial migration's trigger function used SQLSTATE `23001`, which Prisma reports as `P2003`
  "Foreign key constraint violated". Because the migration had already been applied, it was not
  edited (that would change its checksum and force a reset); a second migration,
  `20261006005042_audit_trigger_error_code`, replaces the function with the default `P0001`.
- Custom SQL objects are invisible to Prisma's schema tooling; the integration tests are the source
  of truth for their presence.
- Migrations must never be edited after being applied anywhere; corrections are new migrations.
